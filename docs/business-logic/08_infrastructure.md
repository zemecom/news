# 08. Инфраструктура: Слой ниже PHP

Бизнес-логика, контроллеры и базы данных — это здорово. Но всё это должно где-то запускаться, как-то тестироваться и иметь структуру таблиц. 
Этот слой не принадлежит архитектуре гексагонального монолита, это инфраструктура самого проекта.

## 1. База Данных: Схема и Наполнение

### Migrations (Миграции)
*(Где: `database/migrations/`)*
В проекте используется PostgreSQL. Миграции описывают структуру таблиц.
Важные вещи, которые тут есть:
- В миграции создания `sources` мы дефолтом кладем поле `error_streak = 0`.
- В миграции `news_items` (`create_news_items_table`) мы создаем поле `raw_fingerprint` типа `string` и **сразу вешаем на него `$table->unique('raw_fingerprint')`**. То есть дедупликация гарантируется самой СУБД на уровне индексов, а не только кодом.
- Для хранения `tags` и `source_metadata` мы используем тип столбца `jsonb`. Postgres умеет очень эффективно искать внутри JSONB объектов (в отличие от обычного текстового JSON).

### Seeders (Сидеры)
*(Где: `database/seeders/`)*
Сидеры наполняют базу начальными данными при развертывании проекта (`php artisan db:seed`).
В `DatabaseSeeder.php` мы:
- Запускаем `UserSeeder` (создает пользователя-админа для Filament).
- Запускаем `SourceSeeder` (создает дефолтные источники, например RSS Хабра и пару Telegram каналов).

## 2. Docker: Контейнеризация проекта
Мы не ставим PHP, Postgres или Redis к себе на компьютер напрямую. Всё крутится в контейнерах.
В корне проекта лежит `docker-compose.yml`.

Он поднимает несколько сервисов:
1. `app`: Это образ (Image), собранный из нашего `Dockerfile`. Внутри него крутится PHP 8.5 и RoadRunner.
2. `worker`: Точно такой же образ `app`, но вместо RoadRunner он запускает команду-воркер `php artisan queue:work`, чтобы разгребать RabbitMQ.
3. `postgres`, `redis`, `rabbitmq`: Сервисные контейнеры.

**Важно знать про Docker в нашем проекте:**
Мы не теряем данные при перезапуске контейнеров! В настройках Volumes у нас прописаны пути:
Например, для базы данных: `./.docker-data/postgres:/var/lib/postgresql/data`. Это значит, что файлы базы данных PostgreSQL физически лежат в папке `.docker-data/` в корне твоего проекта (она добавлена в `.gitignore`). Если ты удалишь контейнеры `docker compose down -v`, то твои таблицы **НЕ удалятся**, пока ты не удалишь саму папку `.docker-data`.

## 3. Автоматизация: Makefile
Чтобы не запоминать длинные команды Docker (например: `docker compose exec -it app php artisan migrate`), у нас есть `Makefile` в корне.
Он содержит умные сокращения:
- `make setup-local` — автоматически поднимает контейнеры, устанавливает пакеты composer, делает миграции, сиды, линкует storage и создает Exchange в RabbitMQ. Вся настройка в 1 клик.
- `make ci-check` — прогоняет все тесты и проверки кода.

## 4. Качество кода: Тестирование и Статика
Наш код не ломается невидимо, потому что он обвешан проверками:

### Pest PHP (Юнит и Feature тесты)
*(Где: `tests/`)*
Вместо PHPUnit мы используем `Pest` — современный и элегантный фреймворк.
Единственное правило: **тесты должны лежать так же модульно, как и сам код**. 
Но самое главное в наших тестах — это Architektur Rules (Архитектурные тесты).

### Arch Tests (Стражи архитектуры)
Открой `tests/Feature/ArchitectureTest.php`.
Там написан код вида:
```php
test('domain layers are independent')
    ->expect('Modules\*\Domain')
    ->toOnlyUse('Modules\Shared');
```
Это означает, что во время прогона CI, Pest посмотрит на слой `Domain` у всех модулей и, если найдет там вызов `Cache::get()` (из слоя Инфраструктуры) или вызов `Log::info()`, **тест упадет**.
Эти тесты физически запрещают программисту нарушать правила Гексагональной архитектуры. Ты просто не сможешь закоммитить плохой код!

### Статика: PHPStan, Pint, Rector
Кроме тестов у нас работает:
- `PHPStan` (Type checker) — проверяет, что ты не передаешь `null` туда, где ожидается `string`.
- `Pint` (Linter) — автоматически форматирует код (расставляет пробелы, скобки) под стандарт Laravel.
- `Rector` (Refactoring tool) — автоматически обновляет устаревший PHP код на современные стандарты (PHP 8.5+).

Все эти проверки запускаются через `make ci-check`, и мы обязаны пройти их перед каждым `git commit`.
